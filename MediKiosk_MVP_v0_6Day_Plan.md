## 0. Reality check — read this first

Our PRD is 1,100 lines and describes a system that would take a professional team 3 months. We have **6 days**. That means most of the PRD is *aspirational architecture* (the "north star" we point at in the pitch) and only a small subset is what we actually build.

The MVP is scoped to demonstrate the *core loop* end-to-end for **one department, one chief complaint, in two languages**. Everything else — reception app, phone-upload QR, handwritten OCR, three-department support, third language, real ABDM sandbox — is deliberately **out of scope for v0** and honestly labeled as v1 in the pitch. Judges do not punish honest scoping. They punish half-working promises.

**The demo we are building for:**

> A patient walks up to a browser tab (our "kiosk"). Taps Hindi. Grants consent. Says *"पेट में जलन रहती है, खाना ठीक से नहीं पचता।"* The AI conducts a 6–8 turn adaptive interview covering Agni, Koshtha and Ahara-Vihara. Patient uploads one printed lab report from their phone camera. 90 seconds later the doctor opens a separate browser tab and sees a structured Ayurvedic case summary — and every line of the summary can be clicked to show its source (the exact patient utterance or document region it came from).

That's it. That's the demo. If you can imagine a feature not needed for that sentence, it is out of scope for v0.

## 2. The 6-day sequencing (vertical slices, not horizontal layers)

We are **not** building DB → APIs → frontend → LLM in that order. That's waterfall, and it dies in a hackathon. We build one thin working slice on Day 1 and thicken it each day.

### Day 1 — Walking Skeleton (highest-risk stuff first)

Goal by end of day: a patient can open a browser, click record, say one sentence in Hindi, and the doctor's browser tab shows a hardcoded summary with that sentence in it.

Parallel tracks:
- **Track A (Backend + DB):** Postgres up. Schema from Section 3 created. Two FastAPI endpoints: `POST /session/{id}/turn` and `GET /doctor/session/{id}`. Both return hardcoded data.
- **Track B (LLM):** Draft the interview system prompt for the digestive complaint. Test it in a plain Python script — no API, no DB, just prove the LLM can conduct a 6-turn Ayurvedic interview in Hindi and output structured JSON at the end. **This is the highest-risk experiment. If this doesn't work, we pivot before Day 2.**
- **Track C (Frontend):** Two static HTML+JS pages. Kiosk page with a record button and a message log. Doctor page that fetches and renders a summary. Ugly is fine.
- **Track D (Clinical content):** The team member who's not writing code produces the "Dashavidha split spreadsheet": which parameters are self-reportable vs need photo vs need physician. Writes 10 draft Hindi interview questions for Agni/Koshtha/Ahara. **Must talk to a BAMS student today.**

**Day 1 done means: kiosk page → record → transcript shows on doctor page. End to end. No AI yet, no OCR yet.**

### Day 2 — Real interview

- Wire the Day-1 LLM prompt into `POST /session/{id}/turn` for real. Turn stores in DB.
- Complete interview in one browser session (kiosk asks, patient answers, kiosk asks next, until LLM signals "history complete").
- ASR integrated (Sarvam or AI4Bharat — pick whichever gets us to `audio → text` in under an afternoon; do not fine-tune).
- Touch fallback: when LLM asks a yes/no or MCQ, render buttons.

### Day 3 — Summary + Provenance

- On interview completion, generate the structured summary (allopathic sections + Ayurveda sections).
- **Build the provenance table (see 3.3). Every summary claim links to the transcript turn it came from.**
- Doctor page: render summary. Click a claim → highlight source turn. **This is the moment that wins judges.**
- Consent flow: notice → 3 toggles → save consent record → revocation button on kiosk header.

### Day 4 — Documents (printed only)

- Upload endpoint (`POST /session/{id}/document`). Kiosk file picker + camera capture.
- OCR pipeline (Google Cloud Vision or Tesseract — Vision is 20 minutes to integrate).
- LLM entity extraction (test name, value, unit, reference range **extracted from the document itself, not hardcoded**).
- Facts stored with bounding-box refs → provenance links from summary claims about labs.
- Doctor UI: documents tab, abnormal flags in red.

### Day 5 — Polish, second language, FHIR, demo rehearsal

- English language toggle wired through.
- FHIR R4 bundle generated deterministically from structured summary. Downloadable JSON on doctor page.
- Full end-to-end rehearsal, timed. **Target: patient completes in under 8 minutes.**
- Fix the top 5 things that broke in rehearsal.
- Prepare "demo mode" — cached responses in case AI provider fails on demo day.

### Day 6 — Buffer, bug fixes, pitch practice

- No new features. Bug fixes and pitch rehearsals only.
- If we finish early, ABDM sandbox stub is the *only* additional item allowed.

## 3. Data Model

### 3.1 Design principles (violate these and we lose provenance)

1. **Transcript is stored as one row per turn, not as a JSON blob.** The PRD had `transcripts.turns_json` — this is wrong for us. If turns are inside a JSON blob, we cannot foreign-key from summary claims to individual turns, and provenance breaks.
2. **Every extracted fact from a document is its own row**, not a JSON array inside `documents`. Same reason.
3. **Every summary claim is its own row** and points to either a transcript turn or an extracted fact via a polymorphic `source_type` + `source_ref_id`. This IS the provenance system.
4. **Consent artifact ID is stamped on every row that holds patient data**, from the first migration. If we forget this now, "revocation" becomes a lie.
5. **Timestamps everywhere, UUIDs everywhere, `created_at` and `updated_at` on every table.**

### 3.2 Tables

Postgres 16. All IDs are UUID. All timestamps are `timestamptz` UTC.

#### `patients`
- `id` uuid PK
- `name` text
- `age` int
- `gender` text  -- 'M' / 'F' / 'O'
- `phone` text nullable
- `abha_id` text nullable  -- mock for MVP
- `preferred_language` text  -- 'hi' / 'en'
- `created_at` timestamptz

#### `sessions`
- `id` uuid PK
- `session_code` text unique  -- short human-readable code used in kiosk URL, e.g. "047-K3X"
- `patient_id` uuid FK → patients
- `department` text  -- hardcoded 'ayurveda' for v0
- `language` text  -- 'hi' / 'en'
- `state` text  -- 'started' / 'consented' / 'interviewing' / 'uploading' / 'summarizing' / 'summary_ready' / 'in_review' / 'approved' / 'revoked'
- `priority_flag` boolean default false  -- red flag
- `priority_tier` text nullable  -- 'critical' / 'elevated' / null
- `consent_id` uuid FK → consents nullable  -- filled after consent granted; every downstream write MUST check this
- `started_at` timestamptz
- `expires_at` timestamptz  -- started_at + 30 min
- `completed_at` timestamptz nullable

#### `consents`
- `id` uuid PK
- `session_id` uuid FK → sessions
- `notice_version` text  -- e.g. 'v1.0'
- `language` text
- `scope_intake` boolean  -- mandatory true to proceed
- `scope_document_processing` boolean
- `scope_doctor_sharing` boolean  -- mandatory true to proceed
- `scope_abha_linkage` boolean
- `audio_played` boolean  -- did the notice audio finish playing before consent
- `granted_at` timestamptz
- `revoked_at` timestamptz nullable

#### `transcript_turns`  ← **one row per turn, not a blob**
- `id` uuid PK
- `session_id` uuid FK → sessions
- `turn_index` int  -- 0, 1, 2, ...
- `speaker` text  -- 'ai' / 'patient'
- `input_mode` text  -- 'voice' / 'touch' / null for ai turns
- `text` text  -- the utterance (transcribed for voice)
- `audio_url` text nullable  -- pointer to raw audio blob (kept until session end, then purged)
- `framework_tag` text nullable  -- 'agni' / 'koshtha' / 'ahara_shakti' / 'hpi' / 'past_history' / etc. — SET BY LLM ON EACH TURN so we can filter later
- `asr_confidence` float nullable
- `created_at` timestamptz

**Why turn_index and framework_tag matter:** summary claims will point back here by ID, and the doctor UI needs to be able to show *"this claim came from turn 4, which was tagged 'agni'"*.

#### `documents`
- `id` uuid PK
- `session_id` uuid FK → sessions
- `blob_url` text  -- MinIO or local disk for MVP
- `doc_type` text nullable  -- 'lab_report' / 'prescription' / 'discharge_summary' / 'other' — filled by LLM
- `document_date` date nullable
- `ocr_text` text  -- full OCR dump
- `ocr_confidence_avg` float
- `processing_status` text  -- 'uploaded' / 'ocr_done' / 'extraction_done' / 'failed'
- `uploaded_at` timestamptz

#### `extracted_facts`  ← **one row per fact, not a JSON array**
- `id` uuid PK
- `document_id` uuid FK → documents
- `fact_type` text  -- 'lab_value' / 'medication' / 'diagnosis' / 'procedure'
- `name` text  -- e.g. 'HbA1c', 'Amlodipine'
- `value` text nullable  -- '9.2' or '5mg'
- `unit` text nullable  -- '%', 'mg/dL'
- `reference_range_low` text nullable  -- **extracted from the document itself, not hardcoded**
- `reference_range_high` text nullable
- `is_abnormal` boolean nullable
- `abnormal_severity` text nullable  -- 'borderline' / 'abnormal' / 'critical'
- `source_bbox_json` jsonb  -- bounding box on the document image, for the "click to see source" UI
- `extraction_confidence` float

#### `summaries`
- `id` uuid PK
- `session_id` uuid FK → sessions unique  -- one summary per session
- `structured_json` jsonb  -- the canonical structured summary (sections → claims)
- `markdown_rendered` text  -- human-readable render, cached
- `fhir_bundle_json` jsonb nullable  -- generated by deterministic code, not LLM
- `status` text  -- 'draft' / 'in_review' / 'approved' / 'rejected'
- `doctor_id` uuid FK → doctors nullable
- `doctor_edits_json` jsonb nullable  -- diff of doctor edits vs original AI draft
- `rejection_reason` text nullable
- `generated_at` timestamptz
- `approved_at` timestamptz nullable

#### `summary_claims`  ← **THE PROVENANCE TABLE. Do not skip this.**
- `id` uuid PK
- `summary_id` uuid FK → summaries
- `section` text  -- 'chief_complaint' / 'hpi' / 'agni_assessment' / 'koshtha' / 'ahara_vihara' / 'labs' / etc.
- `claim_text` text  -- one atomic claim, e.g. "Patient reports burning in epigastrium, worse after meals, for 3 weeks"
- `source_type` text  -- 'transcript_turn' / 'extracted_fact'
- `source_ref_id` uuid  -- FK to transcript_turns.id OR extracted_facts.id depending on source_type
- `order_index` int  -- display order within section
- `confidence` float nullable

**How this powers the demo:** doctor clicks a claim → frontend looks up `source_type` + `source_ref_id` → highlights the exact transcript turn or document region. That is the moment that separates us from every other team.

#### `doctors`
- `id` uuid PK
- `name` text
- `email` text unique
- `password_hash` text  -- bcrypt
- `department` text
- `hpr_id` text nullable  -- mock for MVP
- `created_at` timestamptz

#### `audit_logs`
- `id` uuid PK
- `actor_type` text  -- 'patient' / 'doctor' / 'system'
- `actor_id` uuid nullable
- `session_id` uuid nullable  -- most events tie to a session
- `action` text  -- 'consent_granted' / 'consent_revoked' / 'summary_generated' / 'summary_approved' / etc.
- `resource_type` text nullable
- `resource_id` uuid nullable
- `metadata_json` jsonb
- `created_at` timestamptz

We are **not** making this immutable at the DB level in v0. Log to it, don't build the append-only layer.

### 3.3 The provenance layer — how it actually works

This is the single most important part of this document.

**Flow:**
1. Patient answers a question. Answer stored in `transcript_turns` with a fresh UUID.
2. Interview ends. Summary generation prompt receives ALL turns (with their IDs) and ALL extracted facts (with their IDs).
3. LLM is instructed to output JSON where **every claim carries the `source_type` + `source_ref_id` of the turn(s)/fact(s) it came from**. Prompt example:
    ```json
    {
      "section": "agni_assessment",
      "claim_text": "Vishamagni — irregular digestion with post-prandial burning",
      "source_type": "transcript_turn",
      "source_ref_id": "b12f..."
    }
    ```
4. Backend writes each claim as a row in `summary_claims`.
5. Doctor UI renders the summary. Each claim is a `<span data-source-id="...">`. Click it → fetch the source turn/fact → highlight it in the sidebar.

**If the LLM produces a claim without a valid source_ref_id, we drop the claim.** This must be enforced in code. Silent hallucination is unacceptable in a medical context and a judge will find it in seconds.

### 3.4 Entity relationship summary

```
patients ─┬─ 1:M ─→ sessions ─┬─ 1:1 ─→ consents
                              ├─ 1:M ─→ transcript_turns ←─┐
                              ├─ 1:M ─→ documents ─ 1:M ─→ extracted_facts ←─┐
                              └─ 1:1 ─→ summaries ─ 1:M ─→ summary_claims ───┴─┘
                                                              (polymorphic FK: turn OR fact)

doctors ─── M:1 ── departments (hardcoded enum for v0)
audit_logs ── logs everything, no FKs enforced
```

## 5. Definition of Done for the demo

We are done when, in a single unbroken run:

- [ ] Patient opens kiosk URL, sees Hindi/English toggle
- [ ] Picks Hindi, sees + hears consent notice, grants 3 scopes
- [ ] Says one digestive complaint in Hindi
- [ ] AI conducts 6–10 turn adaptive interview covering Agni, Koshtha, Ahara-Vihara
- [ ] At any point, can tap "withdraw consent" and all session data is deleted
- [ ] Uploads one printed lab report photo
- [ ] Sees "please wait" for under 30 seconds
- [ ] Doctor opens separate URL, sees the patient in queue
- [ ] Opens patient — sees structured Ayurvedic summary
- [ ] Clicks any claim in the summary — source utterance or document region highlights
- [ ] Edits one section, approves
- [ ] Downloads FHIR bundle JSON
- [ ] Total patient time from open to complete: **under 8 minutes**

If we hit this list, we have a demo. If we don't hit this list but built five extra features, we do not have a demo.
